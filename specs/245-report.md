# #245 — Лица персоны выводятся по трекам

## Жалоба

При выборе персоны во вкладке Persons лица выводятся вперемешку. Особенно
заметно на EXTRAS: в одном плане несколько разных людей отнесены к одной
служебной персоне, у каждого свой трек, и сортировка только по кадрам мешает
лица разных людей друг с другом.

Требуется: план за планом, внутри плана трек за треком, внутри трека кадр за
кадром.

## Почему это не «ещё один уровень сортировки»

Первое, что приходит в голову, — добавить в сортировку третий ключ. Так и
сделано, но важнее другое: **где живёт порядок**.

У списка лиц сегодня **два** места, где он пересобирается:

1. загрузка списка персоны — три загрузчика;
2. `reorganizeMatrixFaces()` — после переназначения лица перетаскиванием.

Сортировка в загрузчиках (задача #243) чинит только первое. Второе место
пересобирает список и сортирует его **по-старому** — то есть порядок был бы
правильным до первого перетаскивания и «слетал» бы после него. Поэтому
порядок перенесён **в сравнение объекта** (`FaceExt.compareTo`), а не в
загрузчик: он тогда один везде.

## Что сделано

| файл | изменение |
|---|---|
| `modelsext/FaceExt.kt` | новое поле `trackFirstFrameNumber` (по умолчанию — кадр самого лица) и трёхуровневое `compareTo`: файл → трек → кадр → номер лица в кадре |
| `controllers/FaceController.kt` | карта «трек → кадр начала», собирается один раз на загрузку списка; ключ проставляется всем трём перегрузкам `getListFacesExt` |
| `repos/FaceTrackRepo.kt` | `findByProjectId` — треки всего проекта, для списка по всем сериям |

Ключ берётся **один раз на загрузку списка**, а не на каждое лицо:
идентификатор ленивой связи `Face.track` Hibernate отдаёт из прокси без запроса,
а сами треки приходят одним запросом — по файлу для списков «серия» и «план»,
по проекту для списка «все серии».

Лицо без трека (треки ещё не построены) получает свой собственный кадр и
остаётся на своём месте по времени.

## Проверка на живых данных

План с кадра 31454, E03, персона EXTRAS, три трека: 43391, 43392, 43395.

Было (сортировка по кадрам):

```
43391/31454  43392/31474  43391/31474  43391/31474  43392/31494  43391/31494 …
```

Стало (по трекам, внутри трека по кадрам):

```
43391/31454  43391/31474  43391/31474  43391/31494  43391/31514  43391/31514 …
43392/31474  43392/31494  43392/31514  43392/31534  …
43395/31514  43395/31534  …
```

Ключевое свойство: трек принадлежит **ровно одному плану**, поэтому сортировка
по кадру начала трека даёт нужный порядок целиком — планы по кадрам, внутри
плана треки по кадру начала, внутри трека лица по кадрам. Отдельного уровня
«план» не требуется.
