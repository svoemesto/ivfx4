## 1. Что уходит в Python

В json попадают **две разные по происхождению части**, склеенные в один массив
(`RecognizeFaces.kt:152`):

```
gson.toJson(arrFrameFaces + galleryFaces, fileWriter)
```

### 1a. Очередь — неопределённые лица ОДНОГО файла

`RecognizeFaces.kt:52` → `FaceController.getListFacesExtToRecognize(fileExt)`
(`FaceController.kt:200-222`) → `Main.faceRepo.findFacesToRecognize(fileExt.file.id, undefindedPerson.id)`

Нативный запрос (`FaceRepo.kt:108-112`):

```sql
SELECT * FROM tbl_faces WHERE file_id = ?1 AND person_id = ?2
-- ?1 = id обрабатываемого файла, ?2 = id персоны UNDEFINDED
```

Условия отбора: **только `file_id` и `person_id`**. Ни `is_example`, ни `is_manual`,
ни `person_recognized_name` в запросе нет. Тип лица принудительно
переставляется в `UNDEFINDED` перед записью (`RecognizeFaces.kt:54-58`), хотя
запрос и так уже выбрал именно неопределённых.

Запрос на каждое лицо галереи (`FaceRepo.kt:138-141`, производный от Spring Data):

```sql

```

Дополнительное условие отбора — уже в Kotlin: `face.personRecognizedName != ""`

Итоговые условия попадания в галерею:

| Условие | Где задано |
|---|---|
| `person_type = 0` (`PERSON`) | `RecognizeFaces.kt:100` через `PersonType.PERSON` |

**Число запросов на сборку галереи**: файлов × персон = **10 × 70 = 700** нативных

## 2. Область действия галереи: **весь проект**

**Доказательство по коду**: `RecognizeFaces.kt:102` вызывает
`Main.fileRepo.findByProjectId(projectId)` (`FileRepo.kt:25` — все файлы проекта),
а не `findByFileId`. Галерея обходится парами «серия × персона», и в комментарии
`RecognizeFaces.kt:81-84` прямо сказано, что выбор сделан намеренно: серии одного
сериала показывают одних и тех же людей.

**Доказательство по данным** (реальный файл прогона E05, приведён выше):
`fileId` в галерее — `[1, 2, 3, 4]` (E01–E04), а `fileId` в очереди — `[5]`
(E05). Галерея и очередь живут в разных сериях.

Второй файл прогона E03: `fileId` в галерее `[1, 2, 3]`, очереди нет вовсе.

**Ответ**: очередь — один файл; галерея — все файлы проекта. Стоимость шага
определяется размером галереи всего проекта, а не текущей серией.

## 3. Запуск: по одному файлу или по многим сразу

Файлы выбираются **выделением строк в таблице** серий на экране пайплайна, а не
отдельным переключателем RF:

- `ProjectActionsFXController.kt:424` и `:616-633` — обход
  `tblFilesExt?.selectionModel?.selectedItems`, для каждой выделенной серии
  создаётся свой поток `RecognizeFaces`;
- галка `[RF] Recognize faces` — одна на всю операцию (`checkRecognizeFaces`,
  `:287`, `:391`);
- галочка «пересоздать, если есть» (`checkReCreateIfExists`) — единственный
  способ повторно прогнать RF на серии, у которой `hasRecognizedFaces = true`
  (`:616-618`).

**На одном файле запустить можно** — достаточно выделить одну строку. Это видно
по журналу: `run2.log:70` — «строк выделено: 1», и RF шёл на E03.

Потоки выполняются **последовательно**, не параллельно: `RunListThreads` зовёт
`next.join()` (`RunListThreads.kt:38`). При N выделенных сериях галерея
собирается и json пишется N раз, то есть проектная галерея пересобирается
заново на каждую серию.

## 4. Куда девается время

Скрипт: `src/main/resources/com/svoemesto/ivfx/utils/FaceDetector/recognize_faces.py`
(в рантайме — копия в `target/classes/.../FaceDetector/recognize_faces.py`).

### Механика сравнения

- Модели не грузятся вообще: ни детектора, ни эмбеддера, ни SVM-pickle. Только
  numpy и арифметика (`recognize_faces.py:9-21`).
- Галерея нормализуется один раз и склеивается в **одну** матрицу
  `gallery_matrix` (`recognize_faces.py:99`); строки идут подряд по персонам,
  начало каждой персоны запоминается в `group_starts`.
- Сравнение — **попарное, по одному лицу очереди за итерацию**, но не обходом на
  Python: одно произведение матриц `gallery_matrix @ vector` (`recognize_faces.py:129`),
  то есть умножение матрицы на вектор. Лучший вырез каждой персоны берётся одним
  `np.maximum.reduceat` (`:141`), два лучших — `np.argsort` (`:146`).
- Признаётся лицо, если лучший кандидат выше порога `0.45` **и** обгоняет
  второго на `0.05` (`:159`). Константы — `FaceDetection.RECOGNIZE_THRESHOLD`
  и `RECOGNIZE_MARGIN` (`FaceDetection.kt:116, 132`), передаются ключами `-c` и `-m`
  (`RecognizeFaces.kt:174, 176`).

### Предварительной фильтрации нет

- **По размеру / боксу**: в Python фильтра нет вообще. `startX/endX/startY/endY`
  в json присутствуют, но скрипт их не читает. Проверка пропорций `d > 4`
  есть, но она в Kotlin и применяется **после** распознавания, при записи
  результата (`FaceController.kt:33-35, 49-51`).
- **По эмбеддингу**: единственная фильтрация — отброс нулевого вектора
  (`recognize_faces.py:65-66, 124-126`). Никакого LSH, кластеризации, ANN-поиска,
  отсева по персоне нет.
- **Верхней границы числа сравнений нет**: количество сравнений жёстко равно
  `размер очереди × размер галереи`. Ни батчей, ни потоков, ни ограничения.

### Что печатается и куда

Скрипт печатает `[INFO]`-строки в stdout и одну итоговую строку в
`recognize_faces_result.txt` рядом с json (`recognize_faces.py:40-46, 180-181`).
**В журнал приложения stdout не попадает**: `RunCmd` читает вывод процесса, но
печатает его только при ненулевом коде возврата (`RunCmd.kt:46`). Поэтому в
журнале видна одна строка `[RecognizeFaces] Галерея: … Распознано: …`
(`RecognizeFaces.kt:192`).

### Замер на живых данных

Запущен настоящий `recognize_faces.py` из `target/classes` на копии реального
`faces.json` прогона E05 (очередь 13 679, галерея 29 963 из 70 персон).
Копия — чтобы не трогать файлы проекта.

| Галерея | Распознано | Отклонено по порогу | wall-clock | к полной |
|---|---|---|---|---|
| 29 963 (весь проект, 70 персон) | 6 482 | 6 671 | **83.65 с** | 1.00 |
| 14 981 (половина, 45 персон) | 4 477 | 8 808 | **46.10 с** | 0.55 |
| 7 547 (только E04, 49 персон) | 5 962 | 7 336 | **26.01 с** | 0.31 |

Первый прогон воспроизвёл журнал `/tmp/ivfx-run4.log:8278` **дословно**
(6482 / 6671 / 526) — то есть замер стоит на реальном коде и реальных векторах.

Пошаговый профиль (тот же полный файл):

|---|---|

| разбор галереи в массивы | 0.50 с |
| сборка матрицы 29963×512 | 0.57 с |
| **цикл распознавания** (13 679 лиц × 29 963 образцов) | **50.48 с** (3.69 мкс на лицо) |
| `json.dump` (492 МБ) | 20.29 с |
| **всего** | **78.75 с** |

Число парных сравнений: 13 679 × 29 963 = **409 863 877**.

### Линейность

**Да, линейно по размеру галереи.** Механизм: матрица галереи
29 963 × 512 × 4 байта = **61.4 МБ**; она целиком перечитывается памятью на
**каждое** лицо очереди. Это 61.4 МБ × 13 679 ≈ **840 ГБ** трафика памяти,
что и даёт измеренные 50.5 с при эффективной пропускной способности ~16.6 ГБ/с.

Отсюда и замеры выше: **уменьшение галереи вдвое → 83.65 → 46.10 с (×0.55)**,
до четверти → 26.01 с (×0.31). Линейность не чистая: часть времени
(≈27 с из 83.65) — чтение и запись json, они тоже растут с галереей, но по
другой причине (размер файла).

**Цена уменьшения галереи не нулевая:** при галерее из одной серии (E04,
7 547 лиц) распознано 5 962 вместо 6 482 — **минус 8 % полноты при минус 69 %
времени**. При «половине» галереи потеря больше (4 477), потому что половина
списка пришлась на E01–E02 и персон из E03–E04 в ней не оказалось.

## 5. Результат и его применение

### Что возвращает скрипт

1. **Итоговый текст** — в `recognize_faces_result.txt` рядом с json
   (`recognize_faces.py:44-46`): «Галерея: N персон, M отмеченных лиц.
   Распознано: …, отклонено по порогу: …, отклонено по запасу: …».
   Приложение читает его, показывает в надписи и печатает в журнал
   (`RecognizeFaces.kt:189-193`), после чего **удаляет файл** (`:194`).
   Отсутствие файла трактуется как провал скрипта — операция останавливается,
   ничего не перезаписывая (`:201-207`).
2. **Тот же json обратно** — перезаписанный целиком (`recognize_faces.py:176-177`).

Для найденных лиц в json проставляются `personRecognizedName` и
`recognizeProbability` = косинусное сходство (`:160-166`). Остальные поля
не меняются.

### Кто применяет

`RecognizeFaces.kt:209-231`: json читается обратно в Kotlin, и **только записи с
`personType == UNDEFINDED`** отбираются в `facesToUpdate` (`:214`) и проходят в
`FaceController.createOrUpdate` (`:228`).

Галерейные записи в json при этом **не трогаются** — именно для этого они были
помечены типом `PERSON`: скрипт их не меняет, а фильтр их отбрасывает.

### Что происходит с неопределёнными, для которых совпадения нет

- Если ни один кандидат не прошёл порог — запись в json не меняется вовсе:
  `personRecognizedName` остаётся пустым.
- Если порог взят, но запас не набран — тоже остаётся пустым (только счётчик
  `thin_margin`, `recognize_faces.py:168-170`).
- В `createOrUpdate` пустое имя означает `face.person = undefindedPerson.person`
  (`FaceController.kt:59-61, 80`) — **лицо остаётся неопределённым** и при
  следующем прогоне снова попадает в очередь. Домен `faces/domain.md:54`
  формулирует это как инвариант: поле `person` не nullable, нераспознанное лицо
  привязано к служебной персоне «не определено».
- Отдельный случай: при `d > 4` (сильно вытянутая рамка) лицо принудительно
  уходит в `NONPERSON` **вне зависимости от результата** распознавания
  (`FaceController.kt:49-51, 116-117`). То есть потраченное на него сравнение
  не даёт ничего.

Важно: прогресс-бар второй (`Recognize face [i/size]`) обновляется на каждом
лице очереди (`RecognizeFaces.kt:221-226`) — то есть он отсчитывает **применение**,
а не распознавание; всё распознавание идёт внутри одного запуска Python без
обратной связи.

## 6. Замер по базе (живые данные, только SELECT)

```
docker exec -e PGPASSWORD=123 ivfx-db psql -U postgres -d ivfx -c "<запрос>"
```

В проекте один (`project_id = 1`), 10 файлов E01–E10. Лица есть в пяти.

```sql
select fl.short_name, count(*) as all_faces,
       count(*) filter (where f.person_id=1) as undefinded,
       count(*) filter (where p.person_type=0 and p.id<>1) as person_faces,
       count(*) filter (where p.person_type=0 and p.id<>1
                        and f.person_recognized_name<>'') as gallery
from tbl_faces f
join tbl_files fl on fl.id=f.file_id
left join tbl_persons p on p.id=f.person_id
group by f.file_id, fl.short_name, fl.order_file order by fl.order_file;
```

| Серия | всего лиц | неопределённых (очередь) | отмечено персон | **в галерее** |
|---|---|---|---|---|
| E01 | 12 548 | 0 | 8 226 | **8 226** |
| E02 | 8 957 | 12 | 6 832 | **6 832** |
| E03 | 8 724 | 0 | 7 358 | **7 358** |
| E04 | 11 190 | 0 | 7 547 | **7 547** |
| E05 | 13 679 | 6 685 | 6 994 | **6 994** |

Галерея проекта: **36 957 лиц, 70 персон, 5 серий**.

```sql
select count(*) filter (where is_example), count(*) filter (where is_manual), count(*)
from tbl_faces f join tbl_persons p on p.id=f.person_id
where p.person_type=0 and p.id<>1 and f.person_recognized_name<>'';
--   0 |   0 | 36957
```

`is_example` и `is_manual` у всех лиц галереи равны `false` — то есть признаки
«образец» и «ручная отметка» в RF **не используются вовсе**: отбор идёт только
по типу персоны и непустому имени.

### Что это значит для экономии (цифры, не проект решения)

- Доля серии в галерее: **19–22 %**. То есть на текущих данных переход с
  проектной галереи на галерейный набор одной серии уменьшает объём сравнений
  примерно в 4–5 раз (измерение выше: 83.65 с → 26.01 с при спотерянных 8 % полноты).
- Галерея растёт линейно с числом обработанных серий: каждый прогон
  CreateFaces на новой серии добавляет к галерее ~7–8 тыс. лиц. К E10 она будет
  примерно вчетверо больше сегодняшней.
- Сбор галереи стоит 700 запросов на каждый запуск RF — и эти 700 запросов
  повторяются **заново на каждую выделенную серию**, потому что потоки
  последовательные.
- Практический итог на текущем состоянии базы: у E01, E03, E04 очереди нет вовсе,
  и RF на них выходит досрочно (`RecognizeFaces.kt:141-149`). Единственная серия,
  где RF реально работает, — E05, и её прогон стоит ~84 с.

## Что это значит для оптимизации

1. **Стоимость шага линейна по галерее и упирается в память, а не в вычисления.**
   Умножается матрица на вектор: 61 МБ галереи перечитываются на каждое лицо
   очереди, ~840 ГБ трафика на прогон E05. Уменьшение галереи вдвое дало ×0.55,
   до четверти — ×0.31; полнота при этом падает на 8 % (замер на E04).
2. **Галерея — проектная, и это осознанное решение**, а не ошибка: она даёт
   новым сериям образцы. Значит, вопрос не «брать по файлу», а «брать ли по
   персонам, которые реально встречаются в текущей серии» — на текущих данных
   это 49 из 70 персон и 7 547 из 29 963 лиц.
3. **Две трети работы — не распознавание, а json.** На прогоне E05: 6.9 с чтение
   + 20.3 с запись = 27.2 с против 50.5 с на сравнения, при том что галерейная
   часть файла (69 % объёма, 492 МБ) нужна только для чтения, а в результат не
   попадает вовсе.
4. **Отрицательный результат стоит столько же, сколько положительный.** Лицо,
   для которого совпадения нет, остаётся неопределённым и возвращается в
   очередь следующего прогона — то есть неузнанные лица оплачиваются дважды, а
   лица с `d > 4` (вытянутая рамка) отбрасываются в NONPERSON уже после
   сравнения.
5. **Прогресс и время RF не видны.** Ни одного измерения длительности в
   журнале нет, а полоса прогресса отсчитывает только применение результата,
   то есть реально «висящее» состояние — это 84 с чёрного окна; на фоне
   700 запросов на пересборку галереи при каждом запуске это первое, что стоит
   измерить, прежде чем что-то менять.
