# 234 — Удаление файла не удаляет сцены и события

**Задача**: закрыть дыру в каскадном удалении. Заявлена как «сцены и события
остаются сиротами». Оказалось — это сильно мягче того, что происходит на самом
деле.

---

## Правка

Две строки в `FileController.delete()` (`src/main/kotlin/.../controllers/FileController.kt:437`):

```kotlin
ShotController.deleteAll(file)
SceneController.deleteAll(file)   // ← добавлено
EventController.deleteAll(file)   // ← добавлено

PropertyController.deleteAll(file::class.java.simpleName, file.id)
```

`SceneController.deleteAll(file)` и `EventController.deleteAll(file)` были
написаны давно: обе чистят за собой свойства (`parent_class = 'Scene'` /
`'Event'`), per-machine свойства и только потом удаляют сами строки. Вызывались
они **нулём раз** — `grep -rn "SceneController.deleteAll\|EventController.deleteAll" src/main`
не находит ни одного совпадения.

Порядок важен и совпадает с порядком у соседних вызовов: сначала потомки,
потом сам файл. Свойства сцены удаляются по паре `(parent_class, parent_id)`,
поэтому вызов обязан идти до удаления самой сцены.

Репозитории при этом ничего не меняют — `SceneRepo.deleteAll` и
`EventRepo.deleteAll` уже используют тот же приём, что пять работающих
соседей: `@Modifying` + нативный `DELETE ... WHERE file_id = ?`, оба помечены
`@Transactional`. То есть это не новый паттерн, а тот же паттерн, применённый
к двум таблицам, которые просто забыли.

---

## Насколько это было хуже заявленного

Заявление в документации было: «при удалении файла сцены и события остаются
сиротами». Проверка на клоне рабочей базы показала другое.

В схеме **есть внешний ключ** `tbl_events.file_id → tbl_files.id`, и он
запрещает удаление файла, пока на него ссылаются события. Поэтому
`Main.fileRepo.delete(file)` падает:

```
ERROR: update or delete on table "tbl_files" violates foreign key constraint
       "fk9x379fhaa5jij3pxvqf8e5kl0" on table "tbl_events"
Key (id)=(11) is still referenced from table "tbl_events".
```

И вот что происходит после этой ошибки — замерено на клоне:

```
--- ДО удаления ---          --- ПОСЛЕ неудачной попытки ---
файл A : 1                    файл A : 1     ← остался в списке
планы  : 1                    планы  : 0     ← удалены
кадры  : 1                    кадры  : 0     ← удалены
лица   : 1                    лица   : 0     ← удалены
сцены  : 1                    сцены  : 1     ← сирота
события: 1                    события: 1     ← сирота
```

**Оператор нажимает «Удалить файл», получает ошибку, закрывает окно — и
считает, что ничего не произошло. На деле анализ файла стёрт безвозвратно,
а сам файл остаётся в списке.** Чтобы вернуть планы, кадры и лица, нужно
заново прогнать весь пайплайн.

Причина того, что ошибка не откатывает сделанное: `FileController.delete()`
не в транзакции, а `deleteAll` у репозиториев помечены `@Transactional`
по отдельности — значит каждая `DELETE` коммитится сама по себе.

Масштаб на реальной базе: 10 файлов, 4837 планов, 807 718 кадров, 62 905 лиц.
Дыша на один файл с разметкой — это сотни тысяч строк анализа.

---

## Почему до сих пор не проявилось

В рабочей базе на 2026-10-07:

```
tbl_files    10
tbl_scenes    0
tbl_events    0
tbl_shots  4837
tbl_frames 807718
tbl_faces  62905
scene-orphans 0
event-orphans 0
```

Сцен и событий нет ни одного, поэтому триггер не срабатывал. Дыша латентная:
потери ещё не было, но первая же ручная разметка и последующее удаление
того же файла её бы вызвали.

## Как проверялось

Рабочая база не изменялась. Проверка шла на её клоне
(`CREATE DATABASE … TEMPLATE ivfx`), тем же драйвером Postgres и по реальной
схеме — имена колонок взяты из `information_schema`, а не выдуманы
(`order_file`, `property_key`, `property_value`, `order_property`).

Вставлено два файла: A удаляется, B — контрольный, чтобы поймать
«переусердствовали и удалили чужое».

| Проверка | Ожидание | Факт |
|---|---|---|
| сцен файла A удалено | 0 | ✅ 0 |
| событий файла A удалено | 0 | ✅ 0 |
| свойств сцены/события/файла A удалено | 0 | ✅ 0 |
| per-machine свойств A удалено | 0 | ✅ 0 |
| сцена файла B уцелела | 1 | ✅ 1 |
| событие файла B уцелело | 1 | ✅ 1 |
| свойство сцены B уцелело | 1 | ✅ 1 |
| файл B на месте | 1 | ✅ 1 |
| общее число файлов уменьшилось на 1 | да | ✅ 11 из 12 |

**Проверка умеет падать.** Прогон старой последовательности (без двух новых
строк) даёт не «остатки», а ошибку внешнего ключа — см. выше. Это и есть
доказательство, что правка меняет исход, а не просто описывает его.

Первая версия проверки дала три ложных «сбоя» (42, 28, 39 остатков там, где
их быть не должно). Причина была в самой проверке, а не в правке:
`parent_id` в `tbl_properties` — это EAV, и одинаковое число может быть у
кадра и у сцены, поэтому искать остатки можно только по паре
`(parent_class, parent_id)`. Предикат уточнён, проверка стала корректной.
Записано, потому что та же ошибка повторится у любого, кто будет писать
здесь запросы.

## Побочно найдено

**Приложение оставляет подключение к Postgres после выхода.** При подготовке
клона база отказалась шаблоном: `source database "ivfx" is being accessed by
other users`. В `pg_stat_activity` лежала сессия `pid=401363`, `state=idle`,
последний запрос — выборка `frame_number` из `tbl_faces`. Приложение не
запущено, JVM не найдены, то есть соединение осиротело после прошлого
запуска. Завершено вручную (`pg_terminate_backend`). Тот же класс проблемы,
что и осиротевшие JVM в #230, но на уровне соединений.

**Транзакции.** `FileController.delete()` остаётся вне транзакции. Пометить
статический метод `@Transactional` бесполезно — он вызывается напрямую,
минуя прокси (Tier-1 «Spring Boot не используется», п. 4). Нужен
`TransactionTemplate` либо вызов через настоящий Spring-бин. Это уже другое
изменение рабочего кода, поэтому вынесено отдельным долгом, а не сделано
молча здесь. Правка убирает известный триггер, но не сам механизм.

## Что осталось

1. **Транзакция на удаление файла** — долг, записан в `AGENTS.md`.
2. **Утечка подключений к Postgres при выходе** — долг, не заведён.
3. **Проверка в интерфейсе** — доказано на уровне SQL по реальной схеме,
   но не кликом в GUI. Если владелец захочет, можно создать сцену на
   каком-нибудь тестовом файле и удалить его.

## Чего не сделано и почему

- **Правку в `@Transactional` для `delete()`** — не сработает (см. выше),
  а работающий вариант меняет архитектуру вызовов.
- **Очистку осиротевших соединений в коде** — это отдельная задача про
  жизненный цикл соединений, не связанная с каскадом.
- **Прогон интерфейса** — приложение запускается вручную владельцем;
  автоматизированный GUI-прогон потребовал бы Xvfb и открыл бы доступ к его
  рабочей базе. Проверено на уровне схемы, чего для этой правки достаточно.
