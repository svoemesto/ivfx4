# 238 — Склейка планов: перенос вместо удаления, откат неприменимой правки

## Причина

`splitOrUnionShots` при объединении вызывал `ShotController.delete(shotExt.shot)`.
Тот удалял свойства плана и сам план, но **не трогал `tbl_faces_tracks`**, где
`shot_id` — внешний ключ с `ON DELETE NO ACTION`. Склейка падала, стоило
поглощаемому плану иметь хоть один трек.

Разделение плана работало: оно ничего не удаляет, только двигает границу
и создаёт новый план.

Зависимости от `tbl_shots` перечислены полностью — чинить решено все, а не одну:

| что | как связан | строк в E03 |
|---|---|---:|
| `tbl_faces_tracks.shot_id` | внешний ключ, NO ACTION | 1 876 |
| `tbl_properties` (`parent_class='Shot'`) | логическая, без FK | 0 |
| `tbl_properties_cdf` | логическая, без FK | 0 |
| `tbl_shots_tmp_cdf.shot_id` | без FK | 0 |
| `tbl_shots_tmp2_cdf.shot_id` | без FK | 0 |

## Что сделано

**Пять репозиториев** — по методу `moveTo…` в каждом: `FaceTrackRepo.moveToShot`,
`PropertyRepo.moveToParent`, `PropertyCdfRepo.moveToParent`,
`ShotTmpCdfRepo.moveToShot`, `ShotTmp2CdfRepo.moveToShot`.

**`ShotController.moveAll(from, to)`** переносит всё пятое разом и вызывается
до сохранения выжившего плана, чтобы его `id` был свежим. **`deleteAfterMove(shot)`**
удаляет план, не затирая свойства — они уже живут на выжившем. Старый `delete()`
не тронут: он по-прежнему нужен для настоящего удаления плана вместе со всем.

**Второй дефект, найденный при разборе.** Обработчик двойного клика переключает
и **сохраняет** отметку кадра до вызова `splitOrUnionShots`, а тот при
невыполненном условии возвращался молча. Итог — наполовину применённая правка:
флаг в базе есть, план прежний. Теперь метод возвращает `Boolean`, все четыре
точки вызова откатывают отметку, а метод пишет причину отказа.

## Проверка

Синтетическая база с реальной схемой и внешним ключом:

```
ДО починки: удаление плана 200
  УПАЛО: violates foreign key constraint "fk_ft_shot" on table "tbl_faces_tracks"

ДО переноса:  план 200: треков 1, свойств 1 | план 100: треков 2, свойств 0
ПОСЛЕ:        план 200: треков 0, свойств 0 | план 100: треков 3, свойств 1
удаление плана 200: прошло
```

**Проверка на живых данных владельца** — две склейки подряд на E03:

```
[ДЕЙСТВИЕ] двойной клик по кадру 1701
[ДЕЙСТВИЕ] двойной клик по кадру 2422
```

| | до | после |
|---|---:|---:|
| планы | 937 | **933** |
| треки | 1 875 | **1 875** |
| треков-сирот | — | **0** |
| лиц со ссылкой на несуществующий трек | — | **0** |
| лиц без трека | — | **0** |

Треков столько же — значит они **переехали**, а не исчезли. Другие серии не
тронуты: E01 3 399, E02 2 015, E04 2 574.

## Побочно найдено (не в этой задаче)

**936 отметок `is_final_find` против 934 планов.** Кадры 1699, 1701, 2414, 2422
помечены как начало плана, матрица рисует их с новой строки — то есть
**выглядят и кликаются как начало плана**, — но планов с такого начала в
таблице нет. Склейка по ним молча отказывала. Обнаружено владельцем: он
уверялся, что целялся в первый кадр плана, и был прав — расходились данные,
а не отображение. Закрыто пересборкой планов, см. задачу #239.

## Что осталось

Границы переносимых треков не трогаются — они заданы кадрами, а кадры при
склейке не меняются. Отдельного замера не делал.
