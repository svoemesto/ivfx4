# 231 — Линтер Kotlin: ktlint с отпечатком (шаг 3 плана)

**Задача**: шаг 3 предписанного порядка работы («Линтеры»). До него в проекте
не было ни одного линтера: `check-fx-wiring.sh` проверял только связь FXML ↔
контроллер, стиль Kotlin, опечатки и мёртвый код не проверял никто.

## Главное решение: почему отпечаток свой, а не встроенный

В ktlint 1.5.0 есть флаг `--baseline`. **Он не работает.** Проверено на
контролируемом примере: во временный файл внесено 20 нарушений, затем ktlint
запущен трижды —

- без флага — 20 нарушений;
- с `--baseline=<несуществующий файл>` — 20;
- с относительным путём к отпечатку — 20;
- с **абсолютным** путём — 20.

Подавление нулевое. Возможная причина — пути в отпечатке ktlint
(`/opt/ktlint/src/...`) не совпадают с путями проекта, но проверить это без
правки самого линтера было нельзя, а править чужой бинарник неправильно.
Поэтому сравнение сделано своим скриптом.

### Почему отпечаток привязан к счётчику, а не к строке

Встроенный формат ktlint — `<file><error line="N:col" rule="..."/></file>`,
привязка к номеру строки. Для легаси это плохо: любая правка соседних строк
сдвигает нумерацию и весь отпечаток рассыпается. Отпечаток здесь —
`<file name="..."><rule id="..." count="N"/></file>`, то есть пара
**(файл, правило) + счётчик**:

- правка соседних строк отпечаток не ломает;
- переименование правила его не ломает (новое имя = новое правило = новое нарушение);
- новое вхождение **того же** правила в **том же** файле увеличивает счётчик
  сверх отпечатка и попадает в отчёт;
- файл, вычеркнутый из проекта, даёт «долг сократился» — это подсказка
  перезаписать отпечаток, а не ошибка.

### Почему плагин в `pom.xml` не добавлен

Две причины, обе проверены фактами:

1. У Maven-плагина ktlint **нет цели `generateBaseline`** —
   `mvn ktlint:generateBaseline` → `Could not find goal ... among available
   goals check, format, help, ktlint`.
2. `mvn ktlint:ktlint` **не выдаёт идентификаторы правил** — в отчёт попадает
   «ошибка» без указания, какое правило нарушено. Отпечаток без правил
   невозможен.

Добавление плагина дало бы два источника истины (плагин и CLI) с разным
поведением. Плагин из `pom.xml` убран, линтер живёт в `tools/`, версия
зафиксирована файлом. `pom.xml` в итоге **не изменён** — diff по нему пуст.

## Состояние долга

```
файлов с нарушениями: 138 из 138 .kt
всего вхождений:      8036
разных правил:        50
```

Топ-10 правил по числу вхождений:

| Вхождений | Правило |
|---:|---|
| 1474 | `argument-list-wrapping` |
| 950 | `indent` |
| 650 | `function-signature` |
| 561 | `chain-method-continuation` |
| 386 | `wrapping` |
| 359 | `max-line-length` |
| 329 | `binary-expression-wrapping` |
| 303 | `no-blank-line-before-rbrace` |
| 266 | `op-spacing` |
| 239 | `multiline-expression-wrapping` |

Нарушения есть **во всех** 138 файлах — это не «несколько плохих мест», а
стиль всего кода: проект написан компактно, в одну строку, без переносов.
Чинить это сплошным `ktlint -F` нельзя: получится 8 тысяч строк правки
форматирования поверх непроверенного кода, и следующая задача (тесты) не
сможет отличить свою правку от чужой. Правильный порядок — **сначала тесты,
потём долг**, и сокращать его по одному файлу, перезаписывая отпечаток.

## Что проверено и как

| Проверка | Команда | Результат |
|---|---|---|
| Гейт на чистом дереве | `bash tools/check-ktlint.sh` | `новых нарушений нет`, exit 0 |
| Гейт кусается | пустые строки в `utils/ComputerIdentifier.kt` | `standard:no-consecutive-blank-lines — новых вхождений 1`, exit 1 |
| Отпечаток воспроизводим | `bash tools/update-ktlint-baseline.sh` | `записей 8036, файлов 138`, изменение `+0` |
| Сборка не сломана | `mvn -B -q clean compile` | exit 0 |
| Связь FXML жива | `bash tools/check-fx-wiring.sh` | `форма и контроллер связаны` |
| Документация цела | `python3 docs/scripts/lint-docs.py` | exit 0 |
| Секреты не в индексе | `git ls-files` | `.env.local-tracker`, `tools/ktlint/ktlint` не отслеживаются |

Негативный тест — главное доказательство, что гейт вообще работает: без него
«нарушений нет» означало бы «проверка ничего не делает».

Отпечаток перезаписан с отступом (каждый `<file>` на своей строке, 1816 строк
вместо одной) — иначе в `git diff` это была бы одна гигантская строка, в
которой невозможно увидеть, какое правило изменилось.

## Побочно найденный баг CLI: `get-issue` врал о состоянии задачи

Перед `mark-review` состояние 231 проверено не по «команда не упала», а
сырым API — и вывод CLI разошёлся с сервером: `status: "unknown"`,
`assignee: null`, `author: null`, `project: null`.

Причина: OpenProject 13.4.1 отдаёт **встроенное** представление — верхнеуровневые
link-поля `.status`/`.assignee`/`.author`/`.project` равны `null`, а реальные
значения лежат в `._embedded`. Функция `tracker_get_issue` читала верхний
уровень, где ничего нет. Тот же API отдаёт настоящее состояние:

```
status   : In progress
assignee : ai-agent / ai agent
project  : ivfx
```

Исправлено в `tools/tracker-lib.sh`: чтение из `._embedded` с сохранением
верхнего уровня запасным путём (на других версиях и при `?minimal=` статус
приходит строкой). Заодно докинут `type`, который по той же причине был `null`.

Почему это важно именно здесь: правило Tier-1 «Работа идёт через OpenProject»
требует проверять результат `claim-issue` **по имени исполнителя**. Пока
инструмент возвращает `null` вместо имени, правило выполнимо только вручную
через curl — то есть фактически не выполнимо.

## Что осталось

1. **Шаг 4 — тесты.** Их ноль, `src/test` не существует. Это следующий шаг
   предписанного порядка и он важнее долга на 8036 нарушений.
2. **Сокращение долга.** Первым дешёвым кандидатом — `no-unused-imports`
   (176 вхождений): это не переформатирование, а реальный мусор в коде,
   и его чистка безопасна для поведения.
3. **`src/test` в гейте.** ktlint уже предупреждает
   `Source root doesn't exist: src/test/kotlin` — после шага 4 в отпечаток
   попадут и тестовые файлы.
4. **Замечание к отпечатку.** Он покрывает только `src/main/kotlin`. Файлы
   вне этого корня (если появятся) в гейт не попадают.

## Чего не сделано и почему

- **Массовое `ktlint -F` по всему проекту** — см. выше: без тестов такая правка
  непроверяема и неревьюируема.
- **Правка встроенного `--baseline` ktlint** — это правка чужого бинарника;
  причина отказа от него зафиксирована в `docs/guidelines/linting.md`.
- **Лицензионные заголовки и detekt** — не задача шага 3. Шаг покрыт
  минимальным набором: стиль + существующий FXML-гейт + документация.
