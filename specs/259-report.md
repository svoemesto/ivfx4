# #259 — Применение ищет и сохраняет лицо по одному

## Откуда взялась задача

Починка границы транзакции ([#253](#253)) дала ×5,4: с 54 до 9,9 мс на лицо
на прогоне E06. Но эти 9,9 мс — уже не пустые сессии Hibernate. Это два
обращения к базе на каждое лицо:

- поиск лица по ключу «файл + кадр + номер лица» — 2,3 мс, индекс есть;
- сохранение — столько же.

Два по 2,3 и дают десять миллисекунд.

## Что сделано

- **Лица серии читаются одним запросом** и раскладываются в карту по тому же
  ключу, по которому искались поштучно. Записи группируются по файлу, потому
  что json может нести лица нескольких серий, а читать надо лица того файла,
  к которому относится запись.
- **Сохранение одной пачкой** через `saveAll`, а не по одному лицу.
- Отдельно найдено: ветка **создания** нового лица писала базу напрямую,
  в обход общей очереди сохранения. То есть починка не работала бы на создании
  лиц — а это самая крупная операция по объёму, 13 426 лиц на E06.
- Счётчик применения стал сквозным: он сбрасывался на каждой группе файлов.

## Проверка

Гейты: `mvn -B test` — 28 тестов, 0 падений; ktlint — новых нарушений нет;
`check-fx-wiring.sh` — форма связана с контроллером.

**На живых данных не измерялось.** Ожидание — единицы секунд вместо 67, но это
ожидание: починка убирает обращения к базе, а сколько именно занимает пакетное
сохранение, показывает только прогон.

Приложение не пересобиралось — владелец работает с шестой серией.
