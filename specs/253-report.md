# #253 — Применение результата: одна транзакция вместо транзакции на лицо

## Что показал замер

Прогон распознавания на E05, 1 535 неопределённых лиц, распознано 400:

```
[RecognizeFaces] сбор галереи: 14621 мс
[RecognizeFaces] скрипт: 15717 мс, применение: 21466 мс, прогон целиком: 65845 мс
```

Применение — **21,5 секунды из 65,8**, то есть треть всего времени, и
**54 миллисекунды на лицо**. При этом один поиск лица в базе занимает 2,3 мс,
индекс `idx_faces_file_frame_no` есть и работает. Значит время уходит не
туда, куда показывает профайлер запросов.

## Причина

Hibernate в проекте настроен на `enable_lazy_load_no_trans`
(`SpringConfig.kt:98`), а это значит: **каждое ленивое чтение вне транзакции
открывает новую сессию**. Применение шло по одному лицу, то есть по
транзакции на лицо, и на каждое лицо приходилось несколько таких чтений:

- отложенная коллекция персон проекта — её поиск в `getPersonByProjectIdAndNameInRecognizer`;
- отложенные связи лица.

Второе, отдельное: поиск персоны по имени в распознавателе делался **на
каждое лицо**, то есть 400 одинаковых обходов коллекции из 71 персоны.

## Что сделано

- **Пакетное применение в одной транзакции.** Новая функция проходит весь
  результат через `TransactionTemplate`: сессия одна, ленивые чтения
  бесплатны, сохранения идут пачкой, а не по одному.
- **Кеш персон по имени** на время пакетной обработки: 400 поисков → не
  больше 71.
- Проект берётся один раз на лицо, а не на каждое ленивое обращение.
- Переведены **обе** операции: распознавание и создание лиц. У создания лиц
  объект на порядок больше, и выигрыш там должен быть заметнее.

Логика одного лица не тронута — изменилась только граница транзакции.

## Чего этот замер не покажет

На E05 повторный прогон бесполезен для измерения: оставшиеся 1 135 лиц —
это ровно те, которые не распознаются, второй прогон даст «распознано: 0» и
применять будет нечего. **Замер снимается на шестой серии**, где очередь
настоящая.

Ожидаю единицы секунд вместо 21,5 — но это ожидание, а не измерение.
