# Домен: Пайплайн обработки

## Обзор контекста (Bounded Context)

Долгие операции над файлом: извлечение кадров, анализ, поиск планов,
детекция и распознавание лиц, нарезка и склейка. Запускаются все с одного
экрана и выполняются последовательно.

## Dependencies | Зависимости

- `media-file`, `frames`, `shots`, `faces` — операции пишут результат в эти домены
- ADR-0005 — последовательные потоки, отмена не работает
- ADR-0003 — детекция лиц требует кешированных моделей

## Ubiquitous Language | Единый язык

- **Операция**: одна долгая обработка одного или нескольких файлов
- **Индикатор выполнения**: булево свойство «артефакт существует»
- **Пересоздать**: флаг, разрешающий выполнить операцию повторно

## Публичные контракты (API)

### Internal API (для других модулей системы)

`threads/projectactions/` — 16 классов-операций;
`threads/RunCmd.kt` — запуск внешних программ;
`threads/RunListThreads.kt` — последовательный оркестратор.

## Domain Invariants | Инварианты и правила бизнеса

- Операция выполняется, если её индикатор сброшен **или** включён флаг
  «пересоздать». Это единственная идемпотентность в системе.
- Порядок операций жёсткий: превью → мастер-копия → кадры → анализ →
  планы → лица → распознавание → нарезка → склейка.
- Предусловия («нужна мастер-копия», «нужны нарезки без звука») проверяются
  **только человеком** по надписям, программной проверки нет.
- Возвращаемые коды внешних процессов игнорируются: сбой Python не виден
  в интерфейсе. **Исключение — распознавание лиц:** скрипт пишет итог в файл,
  и операция читает его. Без этого результат не был виден нигде, а при
  провале скрипта приложение двадцать минут перезаписывало лица вхолостую.
- **Операция обязана выходить досрочно, когда делать нечего**, и говорить об
  этом прямо. У распознавания лиц два таких случая, зеркачных друг другу:
  - **галерея пуста** — сравнивать не с чем: ни одного лица, отмеченного
    как персона с именем;
  - **очередь пуста** — не с кем: в серии не осталось неопределённых лиц.

  Без второй проверки приложение писало файл с двадцатью с лишним тысячами
  отмеченных лиц, запускало скрипт и читало файл обратно, чтобы не обновить
  ничего. Надпись при этом сообщала, что идёт распознавание.
- **Индикатор выполнения — на диске, не в базе.** Операция считается
  выполненной по наличию артефактов в папке проекта, а не по флагам в
  таблицах: флагов там нет вовсе. Отсюда порядок работы: сначала диск, потом
  чистая база, потом прогон — иначе пайплайн идёт по данным, которых нет.
- Ход долгой операции пишется в журнал, а не только в надпись формы: по
  журналу отвечается на вопрос «что сейчас происходит» без дампа потоков.

### Распознавание лиц: три фазы и три файла

**Rule**: прогон распознавания состоит из трёх измеримых фаз — **сбор
галереи, работа скрипта, применение результата** — и в журнал пишется
длительность каждой плюс итог. Без этого вопрос «сколько заняло
распознавание» не имеет ответа, а оптимизировать нечего.

**Данные идут тремя файлами, а не одним:**

| файл | кто пишет | что лежит |
|---|---|---|
| `faces.json` | приложение | очередь и галерея, **разметка прогона** |
| `recognize_faces_result.json` | скрипт | **только распознанные** лица |
| `recognize_faces_progress.txt` | скрипт | «сделано, всего» для полосы |

Входной файл скрипт **не перезаписывает**. Раньше переписывал, и на E05 это
стоило 20,3 секунды из 78,7: две трети времени уходило на чтение и запись
492 МБ, из которых 69 % — галерея, которая только читается и никогда не
меняется. Приложение затем читала тот же файл обратно, то есть платила за
него дважды.

**Применяются только распознанные лица.** Нераспознанное лицо и так остаётся
неопределённым, а прежний код всё равно прогонял его через поиск в базе и
сохранение без единого изменения.

**Галерея собирается одним запросом**, а не обходом «серия × персона». На
проекте из 10 серий и 70 персон обход давал 700 запросов на каждый запуск, и
они повторялись заново для каждой серии подряд. Условия отбора перенесены из
кода в SQL буквально: расхождение с прежним отбором поменяло бы состав
галереи молча.

**Применение идёт в одной транзакции.** Не в транзакции на лицо. В проекте
включено `enable_lazy_load_no_trans`, то есть каждое ленивое чтение вне
транзакции открывает новую сессию, и по лицу на транзакцию это превращается
в десятки лишних сессий на лицо. Замер: 54 мс на лицо при том, что поиск
лица в базе занимает 2,3 мс.

**Правило: файл на диске проверяется по содержимому, а не по имени.**

Каждая операция читает `faces.json` — результат детекции лиц. Распознавание
раньше писало в **тот же** файл, потому что скрипту нужна и очередь, и галерея
проекта: запись очереди серии плюс 45 тысяч лиц других серий. Имя файла от
этого не менялось, и в штатном порядке «детект → создание лиц» расхождения не
возникало.

Авария 2026-10-08: перезапуск создания лиц после распознавания взял этот файл
и выполнил `face.file = fileExt.file` для **каждой** записи. Шесть серий
потеряли 45 136 лиц — вместе со всеми ручными назначениями, — потому что у
съеденных лиц не оказалось ни одного признака, по которому можно понять, откуда
они: в `tbl_faces` нет колонки с кадром, а в `tbl_faces_tracks` нет серии.
Восстановление шло по сохранившемуся файлу: в нём серия каждой записи была
записана, и 45 136 из 45 136 совпали с базой.

Что изменено:

1. **Распознавание пишет свой вход** в `recognize_faces_input.json`.
   Детектор и перепроверка продолжают писать `faces.json`.
2. **Создание лиц проверяет содержимое**: если в файле есть записи чужой серии,
   операция останавливается и говорит об этом прямо, вместо того чтобы
   молча переписать чужие лица в свою серию.

**Failure**: верить имени файла на диске. Имя — это соглашение, а не
проверка; проверить надо то, что внутри, и отказаться работать, если внутри
не то.

**Failure**: смотреть на время запросов и не смотреть на число запросов.
Профилировщик базы показывает, что поиск быстрый, и по нему кажется, что
всё в порядке — тогда как запросов на лицо десятки, и каждый со своей
сессией.
