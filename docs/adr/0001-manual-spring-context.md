## Context & Problem | Контекст и проблема

Проект на Spring Boot 2.5.6: в `pom.xml` подключены `spring-boot-starter-data-jpa`,
`spring-boot-starter-jdbc`, `spring-boot-starter-validation`, а на `Main` стоит
аннотация `@SpringBootApplication`. По всему видно, что это обычное Spring Boot
приложение, и агент, читая код, будет ждать `SpringApplication.run(...)`,
встроенный сервер и `@RestController`.

Ни одного из этих трёх вещей в проекте нет. Приложение — настольная программа
на JavaFX, которая поднимает контейнер вручную.

## Decision | Решение

Контекст создаётся вручную в `companion object` класса `Main` вызовом
`AnnotationConfigApplicationContext(SpringConfig::class.java)`. Сканирование
компонентов идёт от `@ComponentScan("com.svoemesto.ivfx")` в `SpringConfig`.
Аннотация `@SpringBootApplication` на `Main` мёртвая и ничего не запускает.

Следствия, которые обязаны учитывать разработчики:

- `SpringApplication.run(...)` в проекте нет и не нужен.
- HTTP-сервера нет: ни одного `@RestController`, в `pom.xml` нет
  `spring-boot-starter-web`.
- `@Controller` на классах в `controllers/` — стереотип ради component scan,
  а не признак HTTP-эндпоинтов. Это обычная бизнес-логика со статическими
  методами над репозиториями.
- `@Transactional` **не действует** на FX-контроллерах: они создаются вручную
  (`ProjectEditFXController()`), минуя контейнер, поэтому Spring-прокси над
  ними не создаётся. Транзакция работает только там, где бин взят из контекста.

## Rationale | Обоснование

Мотивация исходная, судя по коду, — приложение запускалось из IDE, а
`main()` JavaFX нужен был для `Application.launch`. Завязка жизненного цикла на
Spring Boot и не потребовалась.

Побочный эффект оказался важнее: раз контейнер поднимается вручную и лениво
(первое обращение к `Main.*` инициирует статический инициализатор), весь
Spring-контекст поднимается уже **после** показа окна.

## Consequences | Последствия

**Отрицательные**

- `@Transactional` на UI-классах — иллюзия: прокси нет.
- Ошибки конфигурации проявляются поздно, при первом касании `Main.*`,
  а не на старте приложения.
- Два независимых соединения с БД: служебное (`H2db.kt`, список баз данных) и
  рабочее (из выбранной пользователем БД).

**Положительные**

- Нет лишнего HTTP-слоя: приложение работает как локальный инструмент.
- Схема БД создаётся из сущностей (`ddl-auto=update`), миграций нет.

**Что делать при изменении**

- Не искать в проекте примеров REST и не проектировать «вызовы напрямую»
  в стиле старого кода как образец.
- `@Transactional` ставить только на бины из контекста.
