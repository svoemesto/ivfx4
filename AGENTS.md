## Tier-1: Сборка и запуск

**Rule**: команды выполняются **полным путём**. В `PATH` maven нет.

```bash
MVN=~/.local/opt/apache-maven-3.9.16/bin/mvn      # Apache Maven 3.9.16
JAVA_HOME=/usr/lib/jvm/jdk-18                      # JDK 18.0.2.1, задано в окружении
$MVN -q compile                                     # компиляция Kotlin
$MVN -q package                                     # сборка jar
bash run-old-app.sh                                 # запуск приложения
```

**Source**: `tools/check-fx-wiring.sh:25` (путь к maven), `pom.xml:207`
(`<source>8</source>`, `<jvmTarget>1.8</jvmTarget>`).

**Failure**: `mvn compile` → `command not found` — maven не в `PATH`, зови полным путём.

**Note**: `pom.xml` собирает под Java 8 (`source/target 8`) на JDK 18. Это
предупреждение, а не ошибка; менять целевой уровень без причины не надо.

## Tier-1: Spring Boot здесь не используется

Это самое неочевидное в проекте, поэтому правило явное.

**Rule**:

1. `SpringApplication.run(...)` в проекте **нет**. Контекст поднимается вручную:
   `AnnotationConfigApplicationContext(SpringConfig::class.java)` в `companion object`
   класса `Main` (`Main.kt:29`). Spring Boot как фреймворк не участвует.
2. `@SpringBootApplication` на `Main` — **мёртвая аннотация**, component scan
   работает от `@ComponentScan` в `SpringConfig`.
3. **HTTP-сервера нет**: ни одного `@RestController` / `@RequestMapping` /
   `@GetMapping`, в `pom.xml` нет `spring-boot-starter-web`. Классы в
   `controllers/` — это бизнес-логика (статические методы над репозиториями),
   а `@Controller` на них навешен по инерции ради component scan.
4. **`@Transactional` не работает на FX-контроллерах**: они создаются вручную
   (`ProjectEditFXController()`), минуя контейнер, поэтому Spring-прокси не
   создаётся. Транзакция действует только там, где бин взят из контекста.

**Failure**: новый код пишет `@Transactional` на FX-контроллере и получает
«транзакцию», которой нет. Или пытается вызвать контроллер по HTTP.

**Source**: `Main.kt:26-48`, `SpringConfig.kt`, отсутствие web-зависимости в `pom.xml`.

## Tier-1: Ловушка FXML ↔ контроллер (главная)

**Rule**: привязка формы и контроллера проверяется перед коммитом:

```bash
bash tools/check-fx-wiring.sh        # 0 — всё связано, 1 — есть разрывы
```

Скрипт проверяет пять вещей: у каждого `fx:id` из формы есть поле в её
контроллере; каждый `onAction="#..."` существует в контроллере; в Kotlin нет
задвоенных сигнатур; формы в `target/classes` не отстали от исходных; код
собирается.

**Failure (как было)**: кнопка «All to EXTRAS» — кнопка нарисована, обработчик
написан, **сборка проходит, нажатие ни к чему не приводит**, потому что в
форме нет `onAction="#..."`. Компиляция такое не ловит никогда.

**Source**: комментарий в `tools/check-fx-wiring.sh:3-9`.

**Правило на будущее**: контроллер формы определяется файлом, в котором вызывается
`FXMLLoader`, а **не** именем класса в `getResource` — имя там принадлежит
владельцу ресурса, а контроллер подставляется отдельно через
`loader.setController(this)`.

## Tier-1: Ловушка пути к ресурсу (`getResource().path`)

**Rule**: `getResource(...).path` **нельзя** передавать в `ProcessBuilder`.

При запуске из jar это не путь к файлу, а строка вида
`file:/...app.jar!/com/.../MediaInfo.exe`, которую `ProcessBuilder` не принимает.
Поломка была и на Windows, если запускать из jar.

**Failure**: `java.io.IOException: Cannot run program "file:/...jar!/..."` —
см. `MEDIAINFO-FIX.md`.

**Source**: `MediaInfo-FIX.md`, `MediaInfo.kt:55`.

## Tier-1: Git-гигиена

**Rule**:

1. `.gitignore` обязателен и **действующий**. Проверено 2026-10-07: до этого
   его не было, а `target/` (77 файлов) и `.idea/libraries/` (181 файл) были
   в индексе.
2. `.gitignore` **недостаточен** для уже отслеживаемых файлов — нужен
   `git rm --cached`. Это повторилось с `deploy/.env` в Karaoke за три года.
3. Не коммитить: `target/`, `.idea/libraries/`, `*.mv.db`, `*.trace.db`,
   `__pycache__/`, скриншоты в корне (`/*.png`).
4. Ресурсы внутри `src/main/resources` **игнорируются исключением** — там лежат
   пиктограммы типов плана (`shot_type_*.png`), они часть приложения.
5. Секретов в коде не держать: пароль БД приходит из БД-списка
   (`tbl_databases`), а не из `application.properties`.
6. Локальные базы H2 (`h2db.mv.db`, `h2db.trace.db`) содержат данные машины и
   не коммитятся.

**Source**: проверка `git ls-files` 2026-10-07: 522 файла, из них 77 в `target/`
и 181 в `.idea/`.

## Tier-1: Тяжёлые артефакты не хранятся в репозитории

**Rule**: модели лиц не коммитятся. Скачиваются один раз и кешируются:

```bash
bash tools/fetch-models.sh              # ~275 МБ, идемпотентно
bash tools/fetch-models.sh --force      # перекачать
IVFX_MODELS_DIR=/path bash tools/fetch-models.sh
```

Кеш по умолчанию — `~/.insightface/models/buffalo_l`: это каталог, который
использует сама библиотека insightface, так что повторной загрузки не будет.
Переопределяется `IVFX_MODELS_DIR`.

Модели: `det_10g.onnx` (17 МБ, SCRFD-10G — детектор) и `w600k_r50.onnx`
(167 МБ, ArcFace — эмбеддинги). Обе — из пакета `buffalo_l`, релиз InsightFace
v0.7. Проверено 2026-10-07: скачанные файлы совпали побайтово с теми, что
раньше лежали в репозитории (`5838f7fe…` и `4c06341c…`).

**Failure**: 184 МБ неизменяемых бинарников в git — каждый клон платит за то,
что не менялось ни разу.

**Source**: `tools/fetch-models.sh`, `FaceDetection.kt` (`MODELS_DIR`,
`missingModels()`), `.gitignore` (`*.onnx`).

## Tier-1: Внешние утилиты берутся из системы

**Rule**: `ffmpeg`, `ffprobe`, `mediainfo` ищутся в `PATH`, затем рядом с
приложением. Встроенных копий в репозитории нет и не должно быть.

Удалено 2026-10-07: `ffmpeg-shared/` (72 МБ), `MediaInfo_CLI/` (7,3 МБ),
`mkvmerge/` (7,9 МБ) — Windows-поставка `.exe` и `.dll`, которая на Linux
не запускается никогда.

**Failure**: вернуть `.exe` в `src/main/resources` — они не работают на
Linux и только раздувают репозиторий.

**Source**: `IvfxFFmpegUtils.resolveBinary()`, `MediaInfo.resolveMediaInfoPath()`.

## Tier-2: Известные долги (не правила, а факт)

- **Тестов нет вообще.** `pom.xml` объявляет `testSourceDirectory`, но каталога
  `src/test` не существует.
- Kotlin-линтера в сборке нет (ktlint/detekt не подключены).
- Живых доков нет.
- Пул потоков отсутствует, отмена операций не работает, дочерние ffmpeg
  не убиваются (`RunListThreads`, `threads/projectactions/*`).
- Каскады JPA покрывают не всё: сцены, события и свойства при удалении файла
  остаются сиротами; нативные `@Modifying @Query("DELETE ...")` идут мимо Hibernate.
- **Закрытие окна не завершает JVM.** Проверено 2026-10-07: окно закрыли, а
  процесс продолжал жить и держал **24,2 ГБ RAM (208% физической памяти)**.
  `Platform.exit()` / `System.exit(0)` по закрытию главного окна не вызываются.
  Пока не исправлено — **после закрытия приложения проверять, что процесс умер**,
  иначе следующий запуск упадёт с `IllegalStateException: The file is locked`
  на `h2db.mv.db`.
- **Python-скрипты распознавания оставляют сирот.** `multiprocessing`-воркеры
  `detect_faces_in_folder.py` не унаследовали завершение родителя: найдены
  процессы, простоявшие 42 часа после его гибели.
