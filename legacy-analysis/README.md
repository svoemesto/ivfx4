## Что за продукт был

**ivfx4** — инструмент кинематографического анализа видеоархива для видеопродакшена.
Он раскладывает видеофайлы на кадры, автоматически находит границы **планов (шотов)**
и **сцен**, детектирует и **распознаёт лица**, сводит всё в реляционную БД, даёт оператору
интерфейс для ручной доводки результата и позволяет **собрать экспортную выборку**
(например: все планы с актрисой X) в один видеофайл.

Пайплайн одной операции:

```
файл на диске
  → Create lossless        (мастер-копия 1920×1080, dnxhd/raw + pcm_s16le)
  → Create frames small    (кадры 135×75 — база для анализа)
  → Create frames full     (кадры 1920×1080 — база для детекции лиц)
  → Analyze frames         (Sikuli: сравнение соседних кадров → simScore*/diff*)
  → Create shots           (пороги diff1=0.4, diff2=0.42 → tbl_shots)
  → Detect faces           (Python + Caffe SSD + OpenFace → faces.json)
  → Create faces           (разбор faces.json → tbl_faces)
  → Recognize faces        (SVM → привязка лиц к персонам)
  → Create shots video     (ffmpeg нарезка планов из lossless, без перекодирования)
  → Create concat          (склейка планов файла, -c copy)
  → Create filter result   (склейка ВЫБОРКИ фильтра — главная фича экспорта)
```

## Решения, которые УЖЕ приняты владельцем (не переигрывать)

1. **Имя проекта: SYP — Show Your Picture.** Смысл: «покажи свою версию фильма» —
   пользователь собирает видео из размеченных кусочков. В домене есть термин
   **shots** — эти кусочки. Папка проекта `/home/nsa/syp`, пакет `com.svoemesto.syp`.
2. **Новый проект создаётся с нуля** в отдельной папке. Не форк старого репозитория,
   не перенос кода — только функциональность.
3. **Стек = Karaoke** (`/home/nsa/Karaoke`): docker-compose, Kotlin/Spring Boot 3.5.6
   (JDK 17), **Vue 3 + Vite**, **PostgreSQL 16**, сырой JDBC, Gradle multi-module.
4. **Публичной части нет.** Веб — только админка. Фронтенд называется
   **`syp-webadmin`** (имя по роли, а не по технологии, как `webvue3` в Karaoke).
   Второй фронтенд-модуль не планируется.
5. **Старый проект — только источник знаний**, `/home/nsa/ivfx4` можно читать и
   «подглядывать», но править там ничего не нужно.

### Ещё НЕ решено — не додумывай

Владелец **не определился с составом Gradle-модулей и docker-контейнеров**. Известно
только имя фронтенда (`syp-webadmin`) и отсутствие публичной части. Разбиение на модули,
состав контейнеров и нужен ли отдельный «веб-бэкенд» — вопрос владельца.

На заметку: в Karaoke `karaoke-web` — это отдельный Spring Boot-модуль (тонкий слой над
`karaoke-app`), который разворачивается на проде, а `karaoke-app` живёт только на
админ-машине. У SYP публичной части нет, поэтому этот дуэт, скорее всего, не нужен —
но решать владельцу. Бэкенд в любом случае нужен один, а nginx-контейнер для статики
фронтенда и проксирования `/api` — в любом случае нужен.

## Критичные ограничения целевого стека

Это не общие соображения, а **жёсткие правила** Karaoke — их нарушение ломает сборку:

| Правило | Что запрещено | Где закреплено |
|---|---|---|
| **Никакого JPA/Hibernate** | `spring-boot-starter-data-jpa`, `import jakarta.persistence`, `import javax.persistence` | `constitution.md` § II, guard `tools/check-no-jpa-imports.sh` |
| **Сырой JDBC** | Персистентность через `KaraokeDbTable` (reflection + diff-based save) или прямой JDBC | ADR-0001 |
| **Рендеринг через melt/MLT** | Прямой ffmpeg для основного рендера (для вспомогательных операций — можно: extract audio, probe, нарезка) | ADR-0002, R-44 |
| **Секреты только через env** | Хардкод паролей БД; `.env`/`do.env` не коммитить | `constitution.md` § VIII |
| **Публичные API с KDoc** | 100 % покрытие KDoc/JSDoc + `@see` на документ фичи | § VI, FR-006 |
| **ktlint / ESLint в CI** | Новые нарушения ломают сборку | § VI, FR-007 |
| **Образы `nginx:stable`, `node:22-alpine`** | `nginx:alpine` (нет bash), `node:latest` | R-04, R-05 |

В Karaoke уже решено то, чего в `ivfx4` не было:

|---|---|---|

## Что взять как есть (ценные находки)

1. **Трёхуровневая модель фильтров** `Filter → FilterGroup → FilterCondition` с И/ИЛИ
   на каждом уровне и 5 типами условий (`Person`, `Person Property`, `Shot Property`,
   `Scene Property`, `Event Property`) — переносится почти 1:1.
2. **Матрица кадров, где граница плана разрывает строку**, а не занимает ячейку,
   и на стыке страниц крайний план дублируется — продуманное решение, не повторять
   ту же ошибку.
3. **Цветовая семантика оверлеев**: красный = нашёл алгоритм, зелёный = сделал оператор,
   оранжевый = отменил, голубой `I` = I-кадр, синий треугольник = есть лица.
4. **Мастер-копия lossless как единственный источник нарезок** — все шоты режутся из
   неё, а не из исходника: даёт единое качество и скорость.
5. **Ручная доводка результата алгоритма**: двойной клик по кадру = граница плана
   (split/union), рисование лица мышью по кадру, drag&drop лица на строку персоны,
   метки «эталон» для обучения SVM.
6. **Идемпотентность операций** через флаги «артефакт существует» + «пересоздать».

## Что переписывать, а не переносить

1. **Персистентность целиком** — JPA → сырой JDBC.
2. **Сетевой слой** — его не было, проектировать с нуля (DTO, валидация, ошибки).
3. **Очередь и отмена операций** — вместо последовательного `sleep(100)`-оркестратора.
4. **Внешние бинарники** — `ffmpeg.exe`/`MediaInfo.exe`/`mkmerge.exe` были внутри JAR
   под Windows; в контейнере Ubuntu всё ставится apt'ом.
5. **Python-транспорт** — был запуск `.cmd` файла; станет `ProcessBuilder` из воркера.
6. **Кроссплатформенность** — парсер ffprobe хардкодил `\r\n`, `getResource(...)!!.file`
   падал бы при запуске из JAR.

## Открытые вопросы к владельцу

Эти семь пунктов блокируют спецификацию — **задай их владельцу до начала проектирования**
(полный список с формулировками — в [00-OVERVIEW.md](00-OVERVIEW.md), раздел 9).

1. **Сценарий доступа**: однопользовательская машина или веб-сервис с несколькими операторами?
2. **Видеоархив**: остаётся на локальном диске с иерархией папок или уходит в MinIO?
3. **Объём обработки**: файлы поштучно или массовая обработка каталога (сотни/тысячи)?
4. **Каталог лиц**: SVM заново на каждый проект или одна модель на всё?
5. **Экспорт**: нужна ли склейка выборки в видеофайл или достаточно выгрузки метаданных?
6. **Сцены/события**: оставить только ручную разметку или добавить автоматическую?
7. **Размер плана** (`ShotTypeSize`: ECU/BCU/CU/MCU/MS/MLS/LS/VLS/XLS) — вводить в новой модели?

## Где смотреть исходники старого проекта

`/home/nsa/ivfx4/src/main/kotlin/com/svoemesto/ivfx/`

| Каталог | Что внутри |
|---|---|

| `threads/loadlists/`, `threads/updatelists/` | асинхронная загрузка данных в таблицы |
| `utils/` | FFmpeg-обёртки, MediaInfo, оверлеи изображений |
| `enums/` | типы планов, персон, папки, контейнеры/кодеки |

(`tbl_projects`, `tbl_files`, `tbl_frames`, `tbl_shots`, `tbl_faces`, `tbl_persons`,
`tbl_properties`, `tbl_filters*` и др.) создавались из entity-классов, отдельной
миграции нет.
